# PokerLost Service Template

This document defines the high-level foundation generated by `serviceTemplate` and the boundaries
that every pristine service preserves.

## Purpose

`serviceTemplate` is the reusable Copier baseline for PokerLost backend services. It generates
infrastructure and general architectural primitives, never a concrete service domain. Its HTTP
wire contract and OpenAPI 3.1 publication are compatible with the authoritative `pypokerlost` SDK
described in `SDK_COMPATIBILITY.md`.

## Generation contract

Copier 9.17.2 asks for one canonical camelCase or PascalCase identity:

```text
service_name
```

It derives `service_slug`, `service_env_prefix`, and `database_name`. PostgreSQL is an
unconditional part of every generated service; there are no architecture questionnaires or
optional primary-storage branches.

Generated services require Python 3.14 or newer. The Python, Ruff, mypy, builder-image, and
runtime-image versions move together; generated source uses a 100-character line length.

Every generated service declares the private `pypokerlost` distribution from the verified
`pokerlost/pypokerlost` GitHub SSH source, pinned to a full commit SHA already published on
`origin/main`. This platform source is constant and does not add a Copier question. Docker builds
forward the SSH agent and trusted `known_hosts` only while the builder resolves dependencies.

## Generated foundation

Every generated service includes:

```text
FastAPI
API/OpenAPI publication foundation and the pinned private pypokerlost SDK
Pydantic v2 and Pydantic Settings
PostgreSQL, SQLAlchemy 2, and Alembic
Logfire instrumentation foundations
Gunicorn with Uvicorn workers and a Typer CLI
Docker and Helm deployment foundations
uv, Ruff, mypy, and pre-commit
```

The source tree separates `api`, `application`, `domain`, `configuration`, `observability`,
`persistence`, and `cli`. The domain foundation contains the immutable internal `ValueModel` base
at `domain/value_model.py` and the deployment `Environment` category at
`domain/enums/environment.py`. The application layer builds its `Command`, `Query`, and `Result`
value bases on `ValueModel` and provides an abstract asynchronous `Handler` contract.

The application foundation also contains the generic keyed business-operation fingerprinting
primitive. It uses HMAC-SHA-256 with deterministic sorted, length-prefixed framing and persists only
the 32-byte digest plus positive key version. Its optional typed secret setting lets pristine
services remain business-free; concrete idempotent services require the secret at composition.

Persistence provides reusable SQLAlchemy metadata, repository, result-reader, and projection
foundations without a concrete model, table, or migration. One request-owned session and
transaction is opened with SQLAlchemy's async context manager: normal exit commits, exceptional
exit rolls back, and context exit closes the session. SQLAlchemy errors are mapped centrally at
the API boundary: `OperationalError` is an availability failure and other `SQLAlchemyError`
instances are sanitized internal failures. Both use `ApplicationResponse`: availability maps to
HTTP 503 and other SQLAlchemy failures map to HTTP 500. The engine boundary narrowly normalizes an
exact driver-level `ConnectionRefusedError` into `OperationalError`; the request dependency does
not translate exceptions.

## Public API contract

- `GET /` is the only path exception. Its operation ID comes from required root settings.
- OpenAPI publication uses its required settings operation for both the operation ID and
  `"/" + operation_id` path; `.env.example` uses `openapi.get`.
- Every API operation ID matches `^[a-z][A-Za-z0-9]*\.[a-z][A-Za-z0-9]*$`: exactly two
  lowerCamelCase-compatible segments and one dot. A non-root path is exactly the operation ID
  prefixed with `/`.
- Business inputs use one named, closed, typed JSON request body; operation transport does not use
  OpenAPI path, query, header, or cookie parameters.
- Every success uses `ApplicationResponse[ResponseType]`; handled errors use
  `ApplicationResponse[None]`.
- Application-owned JSON uses `snake_case`.
- FastAPI generates the base OpenAPI 3.1 document; the template adds only the required
  `x-pokerlost-service.id` platform metadata and preserves FastAPI-generated route metadata.
- Built-in `/openapi.json`, `/docs`, and `/redoc` are disabled; the configured OpenAPI operation
  publishes the wrapped document.
- Public dependencies use PEP 695 aliases with private resolver functions.

The complete artifact naming contract, including API, ORM, projection, base-class, operation
package, and enum conventions, lives only in the generated `AGENTS.md`.

## Generated documentation

- `README.md` is the concise service landing page.
- `docs/index.md` is the documentation home for getting started, API, architecture, development,
  and project-status material.
- Canonical API pages separate the operation contract, `ApplicationResponse`, errors, OpenAPI/SDK
  integration, and the exact pristine public surface.
- Canonical architecture pages separate dependency direction, request lifecycle, and PostgreSQL
  transaction ownership.
- Development pages own commands, contribution and style rules, migrations, and Docker/Helm use;
  project pages describe the actual quality layers and intentionally unfinished service state.
- `AGENTS.md` is the normative shared PokerLost engineering rulebook and links to the detailed
  documentation rules.
- `SERVICE.md` is the service-owned record of concrete purpose, responsibilities, and local rules;
  Copier preserves it during updates.

The standard-library `scripts/check_documentation.py` validates documentation structure,
same-document anchors, the prohibition on relative inter-file Markdown links, the index inventory,
code fences, and repository-safe content. The generated self-documenting
Makefile exposes regular non-mutating checks through `make check` and the complete local hook pass
through `make check-full`.

## Intentionally absent

The template contains no business entities, business categories, authentication or authorization
implementation (including OAuth2, scopes, token verification, authorization policy, security
scheme, or scope registry), credentials, ledger, poker or blockchain behavior, concrete
persistence entity, fake migration, OpenAPI registry, generated tests, or CI/CD. A generated
service adds only the behavior supported by its known `SERVICE.md` responsibilities.

## Ownership

Copier owns and evolves the reusable scaffold. After initial generation, the service owns
`SERVICE.md` and its explicitly requested business implementation. The release history of this
template is recorded in `CHANGELOG.md`; the copy and update procedure lives in
`CREATE_SERVICE.md`.
